# Foreline gauge: INFICON VGC401 (task T30)

The gauge on the foreline of the turbopump hangs on an INFICON VGC401, a single-channel gauge
controller. This page says how the control system reads it: `EPICS/Db/vgc401.db` with the
protocol `EPICS/Db/vgc401.proto` (StreamDevice), the probe `EPICS/ioc/host/inficon_vgc401_probe.py`
for a first contact without an IOC, the simulator `inficon_vgc401`
(`emulation/sim/mist2sim/devices/inficon_vgc401.py`) and the device case
`emulation/devtest/vgc401`. No IOC loads it yet: the lead adds it to the rack IOC.

## Source

INFICON, *Operating Manual, Single-Channel Controller VGC401*, tinb01e1-f (2011-07), for part
number 398-010 and firmware 302-519-E (its page 2). Read page by page from the copy at
manualshelf.com (`https://www.manualshelf.com/manual/inficon/vgc401-single-channel-controller/manual-english.html`);
INFICON's own download was not found. Page numbers below are the manual's own. Chapter 5,
"Communication (Serial Interface)", pages 55 to 75, is the base of everything here.

## What is read, and what is not

**Read only.** The IOC and the probe send requests for readings only: a three-letter mnemonic
without a parameter, then `<ENQ>` for the data (p. 57). They never send a mnemonic with a
parameter, so no setting of the controller changes: not the unit, not the baud rate, not the
set point, not the gauge.

Two things the controller does differently once the IOC (or the probe) has talked to it, both
from the manual and both undone by switching the controller off and on:

- **After power-on the VGC401 sends the measured value every second by itself. "As soon as the
  first character is transferred to the VGC401, the automatic transmission of measured values
  stops"** (p. 55). The IOC's first request ends it. It stays off until the controller is
  switched off and on again, or until a `COM` command starts it, which the IOC never sends.
  If another device listens to that automatic output (a chart recorder program, say), it gets
  nothing once the IOC runs. Its analog output and relays (the "control" plug) are not
  affected.
- **Reading the error word clears it** (p. 63: "The ERROR word is cancelled when read out. If
  the error persists, it is immediately set again."). The IOC reads it every 2 s, so a flag
  that was set once and went away shows in `PRESSURE:foreline:geterror` for up to 2 s.

| Read | Mnemonic (page) | PV |
|---|---|---|
| Pressure and its status digit | `PR1` (p. 60) | `PRESSURE:foreline:getpressure`, `PRESSURE:foreline:getstate` |
| Pressure unit the controller is set to | `UNI` (p. 67) | `PRESSURE:foreline:getunit` |
| Gauge the controller has identified | `TID` (p. 62) | `PRESSURE:foreline:getgauge` |
| Error word | `ERR` (p. 63) | `PRESSURE:foreline:geterror` |
| Firmware number (the controller has no mnemonic for its type) | `PNR` (p. 71) | `PRESSURE:foreline:getversion` |

Not read: the set point and its relay (`SP1`, `SPS`), the filter, correction factor, offset,
degas, the display, the baud rate (`BAU`). Nothing is switched: not the gauge (`HVC`), not
degas.

## Connection

The rear panel has two 9-pin D-Sub connectors that matter here (p. 12, 24, 25): **"CONTROL",
male**, the analog output and the relay contacts (pin assignment p. 24): **not used.** And
**"RS232", female**: the serial line.

Pins of the "RS232" socket (p. 25, "Pin assignment of the female 9-pin D-Sub appliance
connector"):

| Pin | Signal | Pin | Signal |
|---|---|---|---|
| 2 | TXD (the controller sends) | 1 | not connected |
| 3 | RXD (the controller receives) | 4 | not connected |
| 5 | GND | 7 | not connected |
| 6 | DSR | Chassis | screening |
| 8 | CTS | | |
| 9 | GND | | |

Only TXD and RXD are used (p. 12: "only TXD and RXD used"; p. 55: "No hardware handshake").
The manual's "minimum configuration" (p. 25) joins the computer's RXD to pin 2, its TXD to
pin 3 and GND to pin 5, screen to screen.

**Cable: straight (1:1), male to female**, from the controller's female socket to the male
9-pin plug of a USB to RS-232 adapter. The reason: a PC or adapter port (a DTE, EIA-574) has
RXD on pin 2 and TXD on pin 3. The VGC401 sends on its pin 2 and receives on its pin 3, so pin
2 to pin 2 and pin 3 to pin 3 join each transmitter to the other side's receiver. A crossed
(null-modem) cable would join TXD to TXD and nothing would arrive. The adapter's pin
assignment comes from the RS-232 standard, not from the manual: check it on the adapter. The
manual asks for a screened cable (p. 25).

## Line settings

8 data bits, no parity, 1 stop bit, no hardware handshake (p. 55, p. 12). Baud rate: 9600,
19200 or 38400, **a setting of the controller**, 9600 by default (p. 82, default parameters).
The IOC takes it from the port file (`ports.real.cmd`); the probe from its second argument.

Where the owner reads it: in the controller's **Parameter mode**, parameter "Transmission rate"
(p. 44). Parameter mode is reached from the Measurement mode by holding the `para` key for more
than 5 s (p. 31); the `para` key steps through the parameters, the name is shown at least 2 s,
then its value (p. 32). Leave the parameter mode without changing anything (p. 31). The
display symbol of that parameter is printed in the manual, not reproduced here.

Requests end with CR; replies end with CR LF; `<ACK>` is 06 hex, `<NAK>` 15, `<ENQ>` 05 (p. 56).

## The probe (first contact, without an IOC)

Stop the IOC first if it runs: only one program may use the line. On the rack computer:

```
EPICS/ioc/host/inficon_vgc401_probe.py /dev/ttyUSB0            # 9600 baud
EPICS/ioc/host/inficon_vgc401_probe.py /dev/ttyUSB0 19200      # if the controller says so
```

(The device name of the adapter: `ls -l /dev/serial/by-id/ /dev/serial/by-path/`.) Python 3,
standard library only. It runs about 4 s.

What it prints:

1. **Listening, 3 s, nothing sent.** Each line the controller sends by itself, with its time,
   e.g. `0.490 s  '0,7.5000E-03 Torr\r\n'`. Lines here mean: the cable, the baud rate and the
   controller are right, and it was switched on since anybody last talked to it. Nothing here
   is no fault by itself: the controller was asked before (it stops at the first character,
   p. 55), or the cable or baud rate is wrong. Step 2 tells which.
2. **One request each**, two lines per request: the acknowledgement (`'\x06\r\n'` is good,
   `'\x15\r\n'` is a refusal) and the data, each with the time it took and what it means:
   `PR1` the status digit in words and the value in the controller's own unit; `UNI` the unit;
   `TID` the gauge; `ERR` the error flags; `PNR` the firmware number. `NO REPLY` means nothing
   came within 1 s. `NOT THE FORM OF THE MANUAL` means a reply came but does not look as the
   manual describes it: send that line to the lead.
3. `RESULT: n of 5 requests answered in the form of the manual`. Exit code 0 when all five
   answered, 1 otherwise, 2 when the device cannot be opened.

If every request says `NO REPLY`: the baud rate (try 19200 and 38400), the cable (straight, not
null-modem), the device name. Garbage instead of replies: the baud rate.

Try the probe without the controller: `EPICS/ioc/host/inficon_vgc401_fake.py` runs it against a
fake controller on a pseudo-terminal (exit code 0); with `--silent` the fake never answers and
the probe ends with exit code 1.

## PVs (macros DEVICE, default FORELINE, and PORT, default VGC)

The rack IOC loads the file with `DEVICE=PRESSURE:foreline` (the name the plan had proposed for
this pressure), so the PVs there are `PRESSURE:foreline:...`, as in this table.

| PV | Type | Unit | Scan | What |
|---|---|---|---|---|
| `PRESSURE:foreline:getpressure` | calc | torr | 1 s (after each PR1) | Pressure, converted from the controller's unit. NaN and INVALID when not a measurement |
| `PRESSURE:foreline:getstate` | mbbi | | 1 s | 0 Measurement data okay, 1 Underrange, 2 Overrange (MINOR), 3 Sensor error, 4 Sensor off, 5 No sensor, 6 Identification error, 7 Error BAG, BPG, HPG, BCG (p. 60), 8 No reply, 9 Bad reply or disconnected (INVALID) |
| `PRESSURE:foreline:getunit` | mbbi | | 2 s | mbar, Torr, Pascal, Micron (p. 67); another number INVALID |
| `PRESSURE:foreline:getgauge` | stringin | | 2 s | PSG, PCG, PEG, MPG, CDG, BAG, BPG, BPG402, HPG, BCG, noSEn, noid (p. 62) |
| `PRESSURE:foreline:geterror` | mbbi | | 2 s | No error; Controller error (MAJOR); No hardware, Inadmissible parameter, Syntax error (MINOR) (p. 63) |
| `PRESSURE:foreline:getversion` | stringin | | 2 s | Firmware number, e.g. 302-519-E (p. 71, p. 2) |
| `PRESSURE:foreline:_pr1`, `_pr1:status`, `_state`, `_unit:factor` | ai, ai, calc, calc | | | Internal: the value in the controller's unit, the status digit, the state number, torr per unit |

The alarms: a measurement has no alarm. Below or above the gauge's range the value is shown as
the controller sends it, with MINOR (`Underrange` is the normal end of a pump-down with a
Pirani gauge, not a fault). A gauge error, gauge off, no gauge, an identification error, no
reply or a reply that cannot be read give INVALID and a NaN value, never the last or a zero
value. Until the unit has been read once after an IOC start, and whenever it cannot be read or
is a number the database does not know, the pressure is INVALID as well.

Conversion to torr: mbar x 0.750061683 (1 mbar = 100 Pa, 1 torr = 101325/760 Pa), Pascal x
0.00750061683, Micron x 0.001 (p. 41: "Micron (=mTorr)"), Torr x 1.

## One polling cycle

Every second the IOC sends `PR1` CR, waits for `<ACK><CR><LF>`, sends `<ENQ>`, and reads
`x,sx.xxxxEsxx` CR LF: the status digit and the value in the controller's unit (p. 60). The
state follows from the digit, the pressure from the value and the last unit read. Every 2 s the
same dialogue for `UNI`, `TID`, `ERR` and `PNR`. Each wait for a reply is 150 ms at most
(assumed: the manual gives no response time; the probe measures it). In 2 s there are at most
six dialogues; a silent controller costs 6 x 150 ms = 0.9 s, an acknowledgement without data
6 x 300 ms = 1.8 s, plus about 0.11 s of characters at 9600 baud: the cycle fits its 2 s.

A controller that was just switched on sends by itself. StreamDevice throws away what has
arrived before it sends a request. A line that is already on its way when the request goes out
arrives instead of the acknowledgement: that one reading fails (INVALID for one second, state
"Bad reply or disconnected"), and from the next request on the controller is quiet. Asking
rather than listening was chosen because asking also notices a silent controller, and because
the automatic output ends at the first character anyone sends.

## Assumed

- 9600 baud (the factory setting, p. 82) until the owner reads the controller.
- The response time: 150 ms reply timeout, 50 ms between characters.
- Unit 0 "mbar/bar": the serial value is in mbar (the value's exponent covers any size).
- Unit 3 "Micron": "above 99000 Micron the readout automatically changes over to Torr" (p. 41).
  Assumed: this applies to the display, and the serial value stays in Micron. If not, a value
  above 99 torr would read 1000 times too low in Micron. Not the case while the unit is mbar,
  Torr or Pascal.
- The gauge head (the simulator says PSG, a Pirani): the IOC reads it from the controller.
- The simulator's unit texts in the automatic output ("mbar", "Torr", "Pascal", "Micron") and
  the value it sends with status 3 to 7; neither is read by the IOC.
